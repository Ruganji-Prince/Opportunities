# Updates and alerts

`collect-opportunities.yml` runs at minute 17 every six hours (UTC), with manual workflow dispatch. GitHub may delay scheduled runs. Actions must be enabled on the repository. Each adapter reports failure independently, so one broken feed does not erase the others. A total failure fails the workflow and preserves prior success timestamps. Deadline checks and archival run during every collection, at least daily when schedules execute.

Only meaningful record, source-health or notification-state changes create commits. Volatile verification timestamps alone do not. Therefore the site's displayed last successful collection is the last **published** successful collection; later unchanged checks can be seen in Actions logs. The collector calls a reusable Pages workflow after writing data because pushes using `GITHUB_TOKEN` do not themselves trigger another push workflow.

The dashboard updates countdowns and archive membership every 30 seconds using the browser clock. Classification is urgent up to 72 hours, closing soon up to seven days, upcoming up to 14 days, open thereafter, followed by rolling and unknown deadlines. A date-only deadline preserves its calendar date and uncertainty; comparison uses the end of that date in the original zone, or Kigali as an explicitly documented fallback. Exact timestamp deadlines retain their offset. The optional ICS export uses all-day calendar events for date-only dates.

Dashboard banners and card warnings require no credentials. Optional external delivery uses warning thresholds of seven days, three days and 24 hours. Set repository variable `ENABLE_GITHUB_ALERTS=true` to open GitHub Issues using the workflow token. GitHub notification preferences determine whether issue activity sends email or other notifications; the app cannot guarantee those downstream deliveries. The workflow has `issues: write`; ensure Issues are enabled.

Optional Resend email delivery requires Actions Secrets `RESEND_API_KEY`, `ALERT_FROM` (a verified domain sender), and `ALERT_TO`. Never put them in profile/config/frontend files. Both integrations record a key only after a successful provider response. Keys include opportunity, actual deadline, warning threshold and channel, so changed deadlines can be alerted again. After downtime, only the most urgent reached threshold is sent. Delivery IDs are retained in `data/alert_history.json`; private email addresses and credentials are not. Provider/API success means accepted delivery, not guaranteed recipient reading.

External alerts are disabled until configured. No notification is claimed to have been sent merely because a threshold was crossed. A rare interruption after provider acceptance but before state commit can cause a duplicate next run; this is not an exactly-once delivery system.
